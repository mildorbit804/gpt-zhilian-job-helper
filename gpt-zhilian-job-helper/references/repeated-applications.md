# 投过的岗位重新发布

这是已投去重的一部分，不属于经验包。投过的同公司同岗位默认跳过；如果它在投递之后重新发布，并且符合使用者的全部要求，就照常列为候选，同时提醒使用者哪天投过。再投不投由使用者决定。

使用者明确不需要重发提醒、要求所有已投岗位始终跳过时，将配置 `applicationPolicy.reposts` 设为 `skip`。此时下文重发放行与提醒不执行；改回 `remind` 可恢复，原投递历史保留。已有选择不重复询问。

## 什么算重新发布

列表卡片的发布时间晚于最近一次投递，才算重新发布：

- 投递记录有日期：发布时间晚于该日期。投递记录页只显示日期时，按当天整天算，同一天发布的不算。
- 投递记录没有日期：只能确定是在导入名单之前投的。发布时间晚于导入时间才算，提醒里说明日期没记录。
- 卡片没有发布时间，或发布时间早于投递：按已投跳过，不提醒。

原来那条还挂着、没有重新发布的，不提醒。

## 提醒怎么说

重新发布的岗位照常读详情、核查公司，按使用者全部要求判断。被要求排除的不提醒。符合要求的，在候选里加一句：

> 这个岗位你 2030-07-31 投过，现在重新发布了，再投不投由你决定。

没有投递日期时：

> 这个岗位你投过（日期没记录，在 2030-08-15 之前），现在重新发布了，再投不投由你决定。

（日期均为虚构示例。）程序在 `results` 的 `repostReminders` 和对应条目的 `repost.reminder` 里给出这句话，照用即可。不读消息，不推测对方有没有回复。

## 使用者的选择

- **不投：** 用 `rejected add` 记下这家公司这个岗位，`reason` 写“投过的岗位重新发布，使用者选择不投”。以后不再提醒；只限这个岗位，同公司其他岗位照常筛。想改主意用 `rejected remove`。
- **再投：** 使用者自己发送；告知已投后用 `applied add` 记下新的投递日期。不知道确切日期就省略 `appliedAt`，按记账时间算作这次投递的上限。之后同一条发布按已投跳过；原来的投递日期移入该记录的 `earlier` 保留，以后同步名单时页面上的旧日期不会覆盖这次投递。
- **没回答：** 不替使用者决定，候选和提醒照常保留。

## 本地程序

`…` 表示 `python3 <技能目录>/scripts/zhilian.py --project <用户数据目录>`。

同步投递名单时，页面上每条投递记录显示了日期的，一起写进 `appliedAt`（`YYYY-MM-DD` 或带时区的完整时间）；没显示的不写，不编造。日期不能晚于名单读取时间。已有记录没有日期的会补上；已记录的日期不会被更早的日期覆盖。

使用者告知某条记录的投递日期时补记：

```text
… applied annotate --input 补日期.json --confirmed
```

```json
{"company":"虚构示例公司","job":"设计师","appliedAt":"2030-07-31"}
```

只读查看本轮的提醒：

```text
… repeat list --run 本轮名称
```

`find` 与 `results` 使用同一套判断，查到的重新发布岗位也带 `repost` 信息。
